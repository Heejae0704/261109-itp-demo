Okta Identity Threat Protection

Custom SSF transmitter and Universal Logout demo

Follow these steps to show Okta ending a user's session, in Okta and in a custom web app, the moment your own security tool reports a threat through the Shared Signals Framework.

Before you startYou need an Okta org with Identity Threat Protection, a super admin account, a test user who is not an admin, a GitHub repo with this code, and a Railway account. Keep your admin console in a separate browser so the demo doesn't sign you out.
Railway

1. Deploy the transmitter

Create one Railway project and add the transmitter as its first service.

  1. In Railway, create a new project from your GitHub repo. Open the service's Settings›Root Directory and set it to transmitter.

  2. Open Settings›Networking and click Generate Domain. Copy the domain into Transmitter URL above. It becomes the SET issuer.

  3. On your computer, generate a signing key that stays the same across deploys:

    cd transmitter
npm install
npm run genkey

    Copy the single line it prints (it starts with -----BEGIN PRIVATE KEY-----\n).

  4. In Variables, add:

    VariableValue
    OKTA_ORG_URLhttps://your-org.okta.com
    SIGNING_KEY_PEMThe line from npm run genkey
    ADMIN_PASSWORDA password for the transmitter console
    DEFAULT_SUBJECT_EMAILOptional: jane.doe@acme.com
    Don't skip SIGNING_KEY_PEMWithout it the transmitter makes a new key every time it starts, its JWKS changes, and Okta rejects every SET with invalid_key.

  5. After it deploys, open the metadata and check that issuer is your https Railway URL:

    https://ssf-transmitter.up.railway.app/.well-known/ssf-configuration
Railway

2. Deploy the web app

Add a second service to the same Railway project. You'll fill in the Okta client ID and secret after step 4.

  1. Add a new service from the same repo and set Settings›Root Directory to webapp.

  2. Click Generate Domain and copy it into Web app URL above.

  3. In Variables, add:

    VariableValue
    OKTA_ORG_URLhttps://your-org.okta.com
    OKTA_CLIENT_IDFrom step 4
    OKTA_CLIENT_SECRETFrom step 4
    SESSION_SECRETAny long random string

  4. Keep the service at one replica. Sessions are held in memory, so Okta's logout call has to reach the same instance as the browser.

Running locally insteadCopy each .env.example to .env, export the variables and run npm start (transmitter on :4000, web app on :3000). Okta must reach both apps, so expose them with a tunnel such as ngrok or cloudflared and set PUBLIC_URL and APP_BASE_URL to the tunnel URLs.
Okta Admin Console or API

3. Register the transmitter as a security events provider

This tells Okta to trust SETs signed by your transmitter. Pick one way.

  1. Go to Security›Device Integrations, open the Receive shared signals tab, and click Create stream.

  2. Set Integration name to Custom SSF Transmitter.

  3. Choose Well-known URL and paste:

    https://ssf-transmitter.up.railway.app/.well-known/ssf-configuration

    Or choose Issuer URL and JWKS URL:

    Issuer URL
    https://ssf-transmitter.up.railway.app
    JWKS URL
    https://ssf-transmitter.up.railway.app/.well-known/jwks.json

  4. Click Create. The stream shows as Active.

  1. Create an API token in Security›API›Tokens.

  2. Create the provider. The well-known form lets Okta read the issuer and JWKS URL from your metadata:

    bash
    curl -X POST "https://your-org.okta.com/api/v1/security-events-providers" \
  -H "Authorization: SSWS $OKTA_API_TOKEN" \
  -H "Accept: application/json" -H "Content-Type: application/json" \
  -d '{
    "name": "Custom SSF Transmitter",
    "type": "custom",
    "settings": {
      "well_known_url": "https://ssf-transmitter.up.railway.app/.well-known/ssf-configuration"
    }
  }'

    The non-SSF form uses issuer and jwks_url instead:

    json
    "settings": {
  "issuer": "https://ssf-transmitter.up.railway.app",
  "jwks_url": "https://ssf-transmitter.up.railway.app/.well-known/jwks.json"
}

  3. Or use the included script, which reads your metadata so the values always match:

    bash
    cd transmitter
OKTA_ORG_URL=https://your-org.okta.com OKTA_API_TOKEN=00x... \
TRANSMITTER_URL=https://ssf-transmitter.up.railway.app npm run register
# add  -- --jwks  for the issuer/JWKS form,  -- --list  to list providers
About the type fieldOkta's schema describes type as a free-form "application type" and doesn't list allowed values, so custom is a placeholder. If your org rejects it, use the Admin Console tab, which doesn't ask for a type.
Okta Admin Console

4. Create the OIDC web app

  1. Go to Applications›Applications, click Create App Integration, choose OIDC - OpenID Connect, then Web Application.

  2. Under Grant type, select Authorization Code and Refresh Token.

  3. Enter the redirect URIs:

    Sign-in redirect URI
    https://acme-portal.up.railway.app/authorization-code/callback
    Sign-out redirect URI
    https://acme-portal.up.railway.app/

  4. Under Assignments, assign the demo user or their group directly.

    Use explicit assignmentsUniversal Logout doesn't work for custom apps when Federation Broker Mode is on.

  5. Save, then copy the Client ID and Client secret into the web app's Railway variables (OKTA_CLIENT_ID, OKTA_CLIENT_SECRET). Railway redeploys it.

Why the org authorization serverThe app signs users in against your org URL rather than /oauth2/default. Okta signs the Universal Logout token with the org's SSO key and sets its issuer to the org URL, so both use the same issuer and keys.
Okta Admin Console

5. Turn on Universal Logout for the app

  1. Open the app, go to the Sign On tab (called Authentication in some orgs), and in the Logout section click Edit.

  2. Under Global Token Revocation, select Okta system or admin initiates logout.

  3. Set the Logout endpoint URL:

    Logout endpoint URL
    https://acme-portal.up.railway.app/global-token-revocation

  4. Leave Endpoint authentication type as Signed JWT, set Subject format type to Email Identifier, and click Save.

    The app also handles Issuer and Subject Identifier if you prefer it.

Okta Admin Console

6. Add the entity risk policy rule

This rule is what reacts to your SET. A high user risk from your provider signs the user out of Okta and every app that supports Universal Logout.

  1. Go to Security›Entity Risk Policy (or Security›Identity Threat Protection, then Go to entity risk policy) and click Add rule.

  2. Fill in the rule:

    FieldSet it to
    Rule nameHigh risk from SSF provider → Universal Logout
    User's group membership includesAny group, or your demo group
    DetectionInclude → Security events provider reported risk (or Any detection)
    Entity risk levelHigh
    Take this actionLogout and revoke tokens → Universal Logout and Partial Universal Logout

  3. Click Save, then drag the rule above the default catch-all rule, which only logs.

Okta Admin Console · optional

7. Session protection (optional)

Session protection checks risk on each active session. It suits IP or session-level signals such as ip-change and session-revoked. The main demo doesn't need it.

  1. Go to Security›Identity Threat Protection, open the Detection and Response tab, then Session Protection.

  2. Set Status to Enforced (or Monitoring to only log).

  3. Under Session violation detection, click Edit and choose risk level High (or Medium and above).

  4. Under Enforcement settings, keep Okta logout, click Run an additional action, choose App logout, and Save.

Showtime

8. Run the demo

  1. In a private browser window, open the web app and click Sign in with Okta. Sign in as the demo user. Optionally open the Okta End-User Dashboard in another tab of the same window.

    https://acme-portal.up.railway.app

  2. In your own browser, open the transmitter console. Sign in with any username and your ADMIN_PASSWORD.

    https://ssf-transmitter.up.railway.app

  3. Enter jane.doe@acme.com, keep User risk change (Okta) with low → high, and click Sign and send to Okta. You should see HTTP 202, the decoded SET and the compact JWT.

  4. Within a few seconds the Acme Portal tab shows "Your session was ended by Okta Universal Logout" and the Okta dashboard tab asks the user to sign in again. The portal's Universal Logout requests from Okta table shows a 204.

  5. In Reports›System Log, show the chain: security.events.provider.receive_event, then user.risk.detect, then the entity risk policy's logout action.

To send from the command line instead:

bash
cd transmitter
TRANSMITTER_URL=https://ssf-transmitter.up.railway.app ADMIN_PASSWORD=... \
npm run send -- jane.doe@acme.com user-risk-change
Running it againThe policy acts when risk changes to High, so sending "high" again for a user who is already High may do nothing. Reset first: send high → low (or none) from the console, or reset the user's risk in the Admin Console. Then send low → high again.
Reference

SET format Okta accepts

These rules come from Okta's Management API schema for the SSF receiver and the Configure SSF receiver guide. The transmitter already follows them.

Delivery

http
POST https://your-org.okta.com/security/api/v1/security-events
Content-Type: application/secevent+jwt
Accept: application/json

<compact signed JWT>

No API token is needed. The signature, checked against the provider's registered JWKS, is the authentication. Okta returns 202 Accepted with no body on success, or 400 with {"err": "...", "description": "..."}, where err is authentication_failed, invalid_audience, invalid_issuer, invalid_key or invalid_request.

JOSE header

json
{ "alg": "RS256", "typ": "secevent+jwt", "kid": "<kid published in the JWKS>" }

Claims

ClaimValueNotes
isshttps://ssf-transmitter.up.railway.appMust match exactly the issuer Okta stored for the provider.
audhttps://your-org.okta.comYour org URL, not an authorization server URL.
iatNow, in UNIX seconds
jtiRandom UUIDMust be unique. Okta silently ignores a repeated jti.
eventsOne event, keyed by its type URINo top-level sub. The subject goes inside the event.

Event types

This is the complete list in Okta's receiver schema. ⭐ marks the demo trigger.

Console keyEvent type URIFields besides subject and event_timestamp
user-risk-change ⭐https://schemas.okta.com/secevent/okta/event-type/user-risk-changeprevious_level, current_level: none, secure, low, medium, high
session-revokedhttps://schemas.openid.net/secevent/caep/event-type/session-revokedOptional current_ip, last_known_ip, user agents
device-risk-changehttps://schemas.okta.com/secevent/okta/event-type/device-risk-changeprevious_level, current_level
ip-changehttps://schemas.okta.com/secevent/okta/event-type/ip-changeprevious_ip_address, current_ip_address
device-compliance-changehttps://schemas.openid.net/secevent/caep/event-type/device-compliance-changeprevious_status, current_status: compliant, not-compliant
identifier-changedhttps://schemas.openid.net/secevent/risc/event-type/identifier-changedOptional new_value

Every event also accepts initiating_entity (admin, user, policy, system) and reason_admin / reason_user as {"en": "..."}. Other CAEP events such as credential-change, assurance-level-change and risk-level-change aren't in Okta's receiver schema, so the transmitter doesn't offer them.

Subject

json
"subject": { "user": { "format": "email", "email": "jane.doe@acme.com" } }
Email must matchThe email must be a sign-in email of an existing Okta user. If it isn't, Okta still answers 202 but drops the event, and nothing appears in the System Log.

Full example

This is what the console sends by default.

json
{
  "iss": "https://ssf-transmitter.up.railway.app",
  "aud": "https://your-org.okta.com",
  "iat": 1794205775,
  "jti": "51247df5-0996-4552-b1b7-8be2379634d2",
  "events": {
    "https://schemas.okta.com/secevent/okta/event-type/user-risk-change": {
      "subject": { "user": { "format": "email", "email": "jane.doe@acme.com" } },
      "event_timestamp": 1794205775,
      "initiating_entity": "policy",
      "previous_level": "low",
      "current_level": "high",
      "reason_admin": { "en": "Impossible travel and credential stuffing detected by custom XDR" },
      "reason_user": { "en": "Impossible travel and credential stuffing detected by custom XDR" }
    }
  }
}
Why user-risk-change to highOkta turns a provider's SET into the ITP detection Security events provider reported risk (SECURITY_EVENTS_PROVIDER_REPORTED_RISK), logs user.risk.detect, and raises the user's entity risk. The entity risk policy then runs its matching rule, which is where you chose Universal Logout.

Transmitter metadata

GET /.well-known/ssf-configuration, served as application/json:

json
{
  "spec_version": "1_0",
  "issuer": "https://ssf-transmitter.up.railway.app",
  "jwks_uri": "https://ssf-transmitter.up.railway.app/.well-known/jwks.json",
  "delivery_methods_supported": ["urn:ietf:rfc:8935"],
  "authorization_schemes": [{ "spec_urn": "urn:ietf:rfc:7523" }],
  "default_subjects": "NONE"
}

GET /.well-known/jwks.json returns one RSA key with use: sig, alg: RS256 and a kid.

Universal Logout request

What Okta sends to the web app, and what the app checks:

http
POST /global-token-revocation
Authorization: Bearer <JWT, header typ = global-token-revocation+jwt>

{"sub_id": {"format": "email", "email": "jane.doe@acme.com"}}
CheckExpected
Signaturehttps://your-org.okta.com/oauth2/v1/keys
issYour org URL
audhttps://acme-portal.up.railway.app/global-token-revocation
subThe app's client ID
exp, nbf, iatValid, with 60 seconds of tolerance
App responseWhen
204All of the user's sessions were destroyed
401Missing or invalid token
400Malformed or unsupported sub_id
404The user never signed in to this app

The app also accepts {"sub_id": {"format": "iss_sub", "iss": "...", "sub": "..."}}.

SSF Receiver API

MethodPathDoes
GET/api/v1/security-events-providersList providers
POST/api/v1/security-events-providersCreate a provider
GET · PUT · DELETE/api/v1/security-events-providers/{id}Read, replace or delete one
POST/api/v1/security-events-providers/{id}/lifecycle/activateActivate
POST/api/v1/security-events-providers/{id}/lifecycle/deactivateDeactivate

A response has id, name, type, status (ACTIVE or INACTIVE) and settings (issuer, jwks_url, well_known_url). Requests use an admin API token: Authorization: SSWS <token>.

Troubleshooting

SymptomLikely cause and fix
400 invalid_issuerThe SET's iss doesn't exactly match the provider's issuer. Compare the console's Issuer with the provider in Okta (https, no trailing slash). If the Railway domain changed, update the provider.
400 invalid_audienceOKTA_ORG_URL is wrong. It must be the org URL, not /oauth2/default. If your org expects a trailing slash, set SET_AUDIENCE to the org URL with a trailing slash.
400 invalid_key or authentication_failedThe key changed because SIGNING_KEY_PEM isn't set, or Okta can't reach the JWKS URL.
202 but nothing in the System LogThe email isn't a sign-in email of an Okta user, or the jti was reused.
Event logged but no logoutThe entity risk rule doesn't match (check level, detection and rule order), the user was already High, or the user's group is excluded.
Okta signs the user out but the app doesn'tCheck the portal's Universal Logout table. 401: the token check failed; the reason is in the Railway logs, and setting STRICT_LOGOUT_AUTH=false briefly shows the decoded token. 404: the user never signed in to this instance, for example after a redeploy. No entry: the logout endpoint URL in the app's Logout settings is wrong.

Local end-to-end test

The test/ folder runs the whole chain against a mock Okta. The mock checks the header, the RS256 signature against the published JWKS, iss from the well-known config, aud equal to the org URL, a unique jti, the accepted event types and the email subject. It then simulates a "High → Universal Logout" rule and sends a signed global-token-revocation+jwt to the app.

bash
(cd transmitter && npm install) && (cd webapp && npm install) && (cd test && npm install)
bash test/e2e.sh
# ends with: PASS: SET -> Universal Logout ended the app session
ScopeThe mock only models what Okta documents. Risk scoring, policy timing and System Log events in a real tenant still need the walkthrough in step 8.
